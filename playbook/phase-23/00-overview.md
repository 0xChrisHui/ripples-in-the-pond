### 3.3 停止条件（停的是那一条线，其他线照常）

- **B 线**：Turbo 余额不够报价；某风格坏图超过 10 张；同一文件重传后仍失败；读回 2 小时内仍有未通过；写库前快照不是“正好 100 行旧封面”；写库后任一读回断言失败（→ 先自动回滚，再停）。B 停在哪一步，就在报告里写清楚现场和续跑命令。
- **A、D 线（`verify.sh` 判定）**：
  - 已接受基线只有两项：①`src/lib/self-mint`（9）、`src/types`（10）超 8 文件；②2f 里 **`p15:h7:verify-production` 因网络失败**。注意不是整个 2f Gate：`verify.sh:88-92` 把 `p15:h6:verify`（媒体竞速）、`p15:h7:verify-snapshots`（历史快照计划）、`p15:h7:verify-production`（生产读回）用 `&&` 连成同一个失败项，按 Gate 名豁免会放过真实回归。
  - **开工前**先把这三条命令各跑一次，记下现在各自的结果和错误特征（网络类特征：`fetch failed`、`ECONNRESET`、超时）。之后只有“`verify-production` 失败且特征仍是网络类”才算基线；`h6` 或 `verify-snapshots` 失败，或 `verify-production` 出现断言类失败（快照缺失、哈希不符），一律阻止推送。
  - 基线以外的失败，30 分钟内修不好 → 不推送，保留本地提交，写明原因。
- **推送隔离（A、B、D 共用一条 `main`）**：推送会把此前所有提交一起带上。所以任一代码线（A 或 D）因失败没推送时，后面线推送之前必须先处理它的提交——要么修好，要么用 `git revert` 回退它的全部提交（保留历史）——再对**整个待推送范围**重新跑 `verify.sh`；处理不了就**冻结本夜全部推送**，其他线仍可在本地继续做并提交，报告里写明冻结原因和哪些提交没推。B 线的数据库写入不依赖推送，照常记录。

### 3.4 环境注意（都踩过）

- `.env.local` 连的是**生产 Supabase**：B5 是全程唯一允许的写库操作，其余一律只读。
- Turbo、Arweave、Base 的请求要带 `HTTPS_PROXY=http://127.0.0.1:7897 NODE_USE_ENV_PROXY=1`；dev server 也要带，否则 `/score` 显示快照不可用。
- dev server 开着时不要跑 build / `verify.sh`（`.next` 互踩，会出现假的 404）。
- 目录 ≤8 项、代码文件 ≤220 行是 hook 硬线；Bash 一条命令里放多个 heredoc 会整条失败。
- 无头 Edge 帧率很低，测不到自然发生的动画事件；能画出球，可以做截图门禁。
