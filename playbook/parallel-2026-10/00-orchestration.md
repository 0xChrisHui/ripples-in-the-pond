# 2026-10 四线并行总控 — 从共同基线到晨间验收

> 状态：2026-10-02 计划就绪；本轮只写 playbook，尚未建立夜间工作树、启动开发或发布。
> 用户目标：P15 体验修复、P14-H 第 36 圆视觉、P17 原曲收藏与曲目馆、P13 SEMI 接入可以并行推进，次日交付可打开的集成结果与真实未完成项。
> 执行入口：用户明确启动本轮时，按 `K0 → K1 → 四线并行 → K2 → K3`；不自动恢复四个 Phase 的全部历史任务。
> **轻量执行口径**：验证与报告统一服从 `AGENTS.md` §3。各线只测受影响功能；P15/P14-H/P17 的必要视觉断言合入 K2 一次会话，P13 复用资产证明，不另建验收平台。相关安全链路完整检查不等于每条线都跑全仓。

## 1. 并行能保证什么

独立工作树隔离文件与暂存区，唯一文件负责人减少重叠修改，固定接口约定减少功能冲突，总控负责共享接线和最终合并。它不能消除真实业务依赖：P13 的最终名单需要 P17 的真实地址，主网留存需要接收地址、费用边界和签名能力。

一夜交付分两层：

- **默认夜间目标**：可运行代码、局部验证、整合后的本地验收入口、SEMI 对接包；候选视觉和文案可在早上调整。
- **外部完成目标**：两链 35 首真实留存、生产发布、SEMI 正式播放。只有相应输入、权限和明确动作授权已经具备才执行；否则保留 `external_pending`，完成所有不依赖它的工作。

不把“计划写完”“本地代码通过”“主网上线”“SEMI 已支持”写成同一个完成状态。

## 3. K0 — 总控保存现场并冻结共同版本

### K0.1 盘点和暂停同目录写入

1. 总控只读执行 `git status --short`、`git diff --name-status`、`git diff --cached --name-status`、`git ls-files --others --exclude-standard`、`git worktree list --porcelain`。
2. 确认本次参与的进程已停止向原脏目录写入；不能终止不明用途的用户进程。无法确认仍有写入时，不在该目录做快照或合并，受影响的基线准备等待，文档/接口只读工作可继续。
3. 记录当前 HEAD，并只核对本轮必需的首页、播放和钱包接口是否可用。当前版本可支撑任务就选它作为开发起点；仅当必要实现缺失或用户同时要求发布时 fetch 核准相关主线差异，不默认开展分支整合或历史审计。

### K0.2 无损保存未提交进度

- 保存 tracked diff、原暂存区清单、未跟踪文件清单及必需素材校验摘要到本机私有恢复目录；秘密、钱包、环境文件不进 Git 或共享报告。
- 优先沿用已有可恢复快照/显式路径补丁，把本轮必需修改带入一套隔离工作树形成开发提交，原 index、工作区和当前分支保持不动。只有复杂暂存现场确需时才用独立临时 Git index 形成本地 WIP 快照；不把手写快照流水线作为每次开工任务。
- 包含与本轮相关的删除、新建和修改；逐项排除 `.env*`（公开模板例外）、钱包、凭证、`.vercel`、`supabase/.temp`、构建产物、浏览器 profile 和不需共享的大型参考源工程。不能用 `git add .` / `git add -A` 全收。
- 已经提交到旧分支但尚未进入主线的功能同样属于基线候选；WIP 快照只负责保全，**不自动成为发布基线或需要推送的提交**。
- 必需本地音频不适合进 Git 时，用只读素材清单记录来源、目标、大小和 hash，由总控一次性复制到授权测试目录；不得共享可写的素材目录。

### K0.3 冻结可用的开发基线，不预做发布整合

1. 优先选择一套无人使用、干净、版本可核对的现有工作树作集成位；不能挪用仍运行或有用户改动的目录。没有合格目录才新建本轮集成位。
2. 默认从 K0.1 选出的当前可用版本出发，仅纳入本轮必需 WIP。若某个必要接口确实只能从较新主线取得，按依赖最小整合；不能为“追上主线”先搬完全部分叉提交。发布基线在实际发布前另行校准。
3. 保留已有 seek、播放位置恢复、身份/链选择和 `/me` 必需行为。只记录有取舍的差异，不逐个未改文件另写分析报告；发生实际冲突时按功能合并，不整文件覆盖用户进度。
4. 不为凑齐快照吸收无关合约、权限或数据变更；不明确的高风险 WIP 保存在安全快照并从本轮基线排除。只有直接阻断本轮功能时才作为真实阻塞处理。
5. 纳入本轮 playbook 与共享协议。若实际启动指令已包含 P17-A3 的精确架构扩展授权，总控在冻结基线前同步相应 ARCHITECTURE/STACK/CONVENTIONS 条目并记录授权依据，让四线在同一批准版本开始；未获授权则保留门禁。做相关定向检查，只有确实纳入合约/权限等高风险依赖才执行对应完整 Gate。
6. 创建本地基线提交，记录其完整 SHA 为 `BASE_SHA`。这是四条线共同起点；默认不 push、不部署。

**K0 交付**：`reviews/evidence/parallel-2026-10/<runId>/coordinator-baseline.md`，含 SHA、WIP 保存位置（不含秘密）、纳入/排除清单、依赖检查与各工作树绝对路径。基线尚未冻结时不启动四线代码写入。

- dev/build 同一工作树不可同时写 `.next`。worker 只做定向类型、lint、相关测试；确有路由/打包/生产运行时风险的构建集中到 K2 一次，不自动追加全量 verify.sh。

- 不提供生产密钥给只负责 UI/文档的 worker；P13 无外部联系授权时不发送消息、提交 PR 或修改 SEMI 项目。

文件归属在 K0 重新对照实际路径；路径已移动时登记对应新路径，而不是新建旧路径的平行实现。未登记的共享文件先向总控提出接线请求，不自行抢写。

总控的写权限不等于可以与 worker 同时改同一目录。基线冻结后，共享接线默认汇入 K2；确实必须提前交付的接口或约定，由当前目录持有人移交干净 HEAD、暂停写入后，总控串行提交，再把明确 SHA 交给受影响 lane。其余 lane 不变更起点，也不读取尚在编辑的文件。

## 6. 四线并行与两个交接点

```text
K0 共同基线 → K1 文件/环境分配
  ├─ P15-X：布局 / 焦点 / 登录 / 分享 / Score 退场 ─────────┐
  ├─ P14-H：第36圆运动与隐现 ────────────────────────────┤
  ├─ P17：C1 注册表接口 → 原曲播放/曲目馆/铸造 → C2证据 ─┤→ K2集成 → K3晨间验收
  └─ P13：现有资产盘点 → 消费C1 → 接入包 → 消费C2验收 ──┘
```

### C1 — 早交付公开注册表

P17 优先产出 [共享合同](./10-shared-contracts.md) 的类型、验证器、真实现有资产来源和可消费函数；创建只包含注册表基础的独立提交。总控记录 C1 SHA；P13 合入该指定提交后继续导出/校验，不等待新合约部署。

P13 等 C1 时可完成既有协议盘点、真实 metadata 媒体类型检查、对接说明和验收设计，不能用假地址充当生产清单。

P17 是原曲资产与永久资源证明的生产者；P13 默认消费同源证据，只检查导出一致性。资源 URI/hash、相关源码/依赖/环境未变时不重复下载或重跑；缺失、冲突或有变化的项才定向核验。动态持有人/余额/权限等在真实操作和钱包验收前刷新，不用旧证明替代。

### C2 — 地址与链上凭证移交

P17 完成某一网络的真实部署/留存证据后，更新同一注册表并交付 C2 SHA 与 revision。P13 按新 revision 重生成清单并比对曲目页；未部署网络继续标记未完成。C2 可以按网络分批，不能把 OP 完成写成双链完成。

两处共用 UI 接线在 K2 完成：导航新增“曲目”和唱片视觉/播放互斥。不让这两个文件阻止四条线其他模块并行开发。

## 7. K2 — 总控集成一次

1. 确认目标 worker 已停止写入并交付干净 HEAD；保留其分支和工作树，不能删除以求整洁。
2. P15 位移交后，从共同基线创建唯一集成分支 `codex/night-integration-<runId>`，按 **P15-X → P14-H → P17（含 C1/C2）→ P13** 合并已验证提交。使用可审阅的正常合并；P13 曾合入的 C1 具有相同提交身份，避免重复应用。
3. 对冲突逐项按文件负责人和共享合同处理，禁止使用整树 `ours/theirs`。任何内容冲突都不能通过删功能、删测试或替换永久地址解决。
4. 总控完成导航入口、公共播放互斥、共享场景接线；公共接口变更立即重跑相关调用方测试。
5. 按相关源码/依赖/配置/环境复用证据，commit SHA 改变本身不触发重验。只补集成影响项；路由/打包等风险需要时集中 build 一次（P17 新路由属于此类），不追加无关 Forge 或全量 verify.sh。资产安全只检查相关链路。
6. P15-X、P14-H、P17 的必要视觉断言合入一个集成服务、一次浏览器会话；先已有有效证据就只补交叉项。P13 清单无须另开浏览器，真实 SEMI 适配另在实际钱包验收。工具故障有充分替代证据就结束，没有就如实列未验，不扩建环境。
7. 产出集成 SHA、可访问本地 URL、启动命令与 [晨间验收](./30-acceptance.md) 结果。无权启用的外部动作保持关闭。

合并后的类型/功能问题仅修当前新改动及必要接口。遇到无法安全解决的单线冲突，保留该线提交，继续其他可独立线；在报告中列未合入项，不宣称四线全部成功。

## 8. K3 — 停点与发布边界

- 默认交付停点是集成结果可本地查看、证据完整、未知项列清；不自动等到早晨、不做无请求的周期监控。
- 夜间需要生产部署时，执行清单必须明确包含该动作。总控临发布前再次 fetch、比较最新生产分支；若其间有新提交，集中适配一次并检查受影响功能。
- 含合约、数据库、资金、权限或永久上传的批次保留完整高风险 Gate；不会被普通 UI“快发”规则覆盖。
- SEMI 实际集成缺对方权限时，交付 ready-to-send 对接包并标记 external_pending；不假定对方会在夜间完成。
- 用户未给创作手记时，页面可展示真实“创作手记尚未提供”状态并保持布局；不可伪造艺术家文字。不得以此阻止曲目试听和链上凭证完成。
- 费用上限、留存接收钱包、不可替代签名或原曲授权不明确时，停相关链写入，继续本地开发和验证。

## 9. 启动前自检与最终交付

启动条件：共同基线可复跑、四线目录独立、公共文件唯一负责人、C1/C2约定一致、测试数据隔离、执行权限清单有明确边界。缺一项只暂停相应写入，不无故暂停所有研究/文档工作。

总控最终只需汇报：集成入口、完成需求编号、已验证证据、未完成的真实外部项、下一步。详细步骤保存在四线 handoff 与晨间清单，用户无需阅读整夜日志。
