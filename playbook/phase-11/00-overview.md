# Phase 11 — 全站「夜塘唱片册」UI 再设计

> **启动日期**：2026-09-01
> **产品范围**：全局视觉基础、`/score/[id]`、`/me`、`/artist`、登录、播放器、状态页与分享视觉
> **视觉锚点**：生产首页的夜塘世界 + 已上链 Score Decoder 的编辑式唱片页面
> **前置证据**：`reviews/2026-09-01-phase-11-design-inventory.md`
> **用户新增决策**：`/score/[id]` 不再用旧页面包裹一个内嵌播放页；Decoder 播放页直接成为作品页主体，合约地址、交易哈希、分享等信息整合进同一页面。

---

## 1. 三句话概念简报

1. P11 不是给三张旧页面换皮，而是让首页、唱片、个人档案和艺术家叙事属于同一个作品世界。
2. Score Decoder 已经具备最明确的唱片气质，因此它既是 `/score/[id]` 的主体，也是 P11 内页视觉系统的主要参考。
3. 永久上链的 Decoder 和可持续演进的站内页面职责不同：前者保证作品永远能播放，后者负责导航、身份、分享和链上凭证。

---

## 2. P11 是什么 / 不是什么

### 是

- 建立一套全站可复用的深色编辑式视觉基础。
- 把 `/score/[id]` 重做为 Decoder-first 的数字唱片页。
- 把 `/me` 重做为“我的音乐档案”，统一唱片、素材和创作状态。
- 把 `/artist` 重做为“108 首长期项目”主叙事、艺术家身份为序章的公开页面。
- 统一登录、全局播放器、导航、加载、空状态、错误、404、OG 与海报。
- 移动端从 375px 起设计，所有主要触控目标至少 44×44px。

### 不是

- ❌ 不重做 P8 水体、球体、涟漪与首页 WebGL 场景。
- ❌ 不改变 P9 的 33 键音效、动画映射与演奏编舞。
- ❌ 不修改合约、不新增链上字段、不迁移已铸 NFT。
- ❌ 不新增业务能力（混音、RemixNFT、二级市场、评论、关注）。
- ❌ 不安装新 UI / 动画依赖；优先使用 React、Tailwind、CSS 和现有 Web Audio。
- ❌ 不把内页做成通用 Web3 dashboard 或 SaaS 卡片墙。

## 3. 冻结的设计方向

### 名称：夜塘唱片册（Night Pond Editorial）

它由两种美学组合：

- **Editorial / Magazine**：唱片内页式大标题、细分隔线、编号、注脚、作品凭证和非对称版式。
- **Japanese Minimalism / Ma**：安静留白、低速淡入、少量水光、不用密集卡片填满空间。

### 视觉语言

| 维度 | 规则 |
|---|---|
| 背景 | 墨黑到深蓝灰，允许轻微水光/颗粒，不复制首页 WebGL |
| 主文字 | 暖白，不用纯白大面积刺眼 |
| 次文字 | 蓝灰，但关键信息不得低于可读对比度 |
| 强调 | Decoder 的雾蓝为功能强调；暖金只用于作品编号/铸造完成等稀有节点 |
| 字体 | Cormorant 负责作品标题；Azeret Mono 负责编号/链上数据；中文正文使用可读 sans fallback |
| 边界 | 1px hairline、少阴影、圆角克制；只有“实体唱片/操作面板”才有容器 |
| 动效 | 400–600ms 缓慢淡入/亮起；无弹跳；reduced-motion 下取消位移与循环呼吸 |

### 反例

- 紫色渐变 + 玻璃卡片矩阵。
- 所有信息都塞进圆角卡。
- 为了“水塘感”在每张内页加载完整 Three.js 水面。
- 关键数据用 `text-white/20` 隐到几乎不可见。

## 4. 页面角色

| 页面 | 第一主角 | 用户主要动作 | P11 成功信号 |
|---|---|---|---|
| `/` | 夜塘与演奏 | 选曲、播放、演奏、进入个人页 | UI 更易发现但不遮挡水塘 |
| `/score/[id]` | 一枚可播放的永久数字唱片 | 播放、理解作品、验证链上凭证、分享 | Decoder 就是页面主体，无套娃感 |
| `/me` | 用户自己的音乐档案 | 找到刚创建/上链中的作品、播放、继续铸造 | 三类对象和状态一眼可分 |
| `/artist` | 108 首长期创作计划 | 理解项目、查看进度与参与规模 | 不再像统计后台，不再承诺空投 |

## 5. 冻结决策

### D1 — 首页核心冻结

P11 只改首页 UI overlay（品牌、导航、组别、教学、登录），不改水体、球、P9 动画及调参真值。

### D2 — `/score/[id]` 采用 Decoder-first

- 移除旧的大封面 + 标题 + 360px `ScorePlayer` 外壳。
- 已上链作品使用该 NFT metadata 中**精确钉死的 `animation_url`**，全幅展示 Decoder。
- 不用当前环境变量重新拼 Decoder URL，否则老 NFT 会被错误地播放成“最新版”。
- Next.js 原生层负责：回到水塘、作品编号、曲名、创作者、Token ID、OP Mainnet、ScoreNFT 合约地址、铸造交易哈希、tokenURI/metadata、分享与下载海报。

### D3 — 不修改永久 Decoder 来迁就站内页面

已铸 NFT 的 Decoder 不可改。站内页面必须兼容不同历史 Decoder 版本；未来上传新版 Decoder 只影响未来铸造，不反写老 NFT。

### D4 — 不做双播放器

进入 `/score/[id]` 时暂停站内 `PlayerProvider` 的旧播放；作品播放只由 Decoder 承担，BottomPlayer 不得覆盖或与 iframe 同时出声。

### D5 — `/artist` 默认以 108 首项目为主角

艺术家本人是序章与署名，108 首计划、章节、进度和作品关系是页面主体。若用户在 P11-D0 改为“艺术家本人优先”，只调整叙事层级，不推翻视觉基础。

### D6 — 主网不做空投

`/artist` 的“下次空投 / 每 36 首触发空投”必须删除。36/72/108 可保留为创作章节或里程碑，但不能继续表达空投承诺。

### D7 — 移动端先行

每个组件先以 375px 单列设计，再加 `min-width` 断点；桌面版不能反向缩成手机。

### D8 — 零新依赖

本 Phase 不装 Framer Motion、图标库、组件库或状态库。若现有栈无法满足某个必要能力，必须越界停并单独报批。

按 `AGENTS.md`，本轮不擅自修改 `docs/ARCHITECTURE.md`。进入 P11-B 代码前必须：

```text
P11-A 视觉基础
   ├──► P11-B /score（第一张样板页）
   │       └──► P11-E 的 OG / 海报
   ├──► P11-C /me
   ├──► P11-D /artist
   └──► P11-E 登录 / 播放器 / 状态页 / 首页外壳
                    └──► P11-F 全站 Gate
```

为什么 `/score` 先做：它公开、无需登录、有真实 `score/1` 与 `score/2` 可验，同时能一次确定页面外壳、作品排版、播放器关系、分享和链上数据样式。

## 9. 全局工程规则

1. 每个 Step 都要写明 `📦 范围`；越界立刻停。
2. 代码文件 ≤220 行，API route ≤270 行，目录每层 ≤8 文件。
3. 新公共组件按领域进子目录，禁止继续把 `src/components/me` 或 `app/score/[id]` 根目录塞满。
4. 不保留新旧两套 UI 长期并存；新页验收通过后移除死组件与死样式。
5. 所有动画支持 `prefers-reduced-motion`。
6. 所有 fetch/iframe/认证状态都有 loading、error、empty 或 degraded 反馈，禁止 `return null` 白屏。
7. 每步 `bash scripts/verify.sh`；失败立刻停，不改相邻文件救火。
8. 每个页面完成后做 375 / 390 / 768 / 1440 四档截图和交互实测。
9. 每个 Step 补齐 walkthrough / LEARNING / ERRORS（如适用）；只有用户明确说 `commit` 时才提交，commit message 使用中文。
