## C8 — localStorage JWT → httpOnly 评估 ✅（结论：维持现状，理由留档）

**现状**：自签 RS256 JWT（7 天）存 localStorage `ripples_auth_jwt`，请求经 Authorization
header 携带（不进 URL ✓）；已有 jwt_blacklist 撤销机制。风险 = 站内 XSS 可读令牌。

**改造成本**（httpOnly cookie）：登录端点改 Set-Cookie + `authenticateRequest`/middleware
改读 cookie（兼容 Privy 双源）+ useAuth 客户端登录态改 `/api/me` 探活（不能再读 token）
+ 服务端登出端点 + CSRF 面浮现（cookie 自动携带，需 SameSite/CSRF token 配套）
≈ 三层 4-5 文件、1-1.5 天 + 全登录链路回归。

**风险现实评估**：
- XSS 注入面窄：站内无 UGC 富文本（事件数据是受控 JSON 渲染，无用户可控 HTML 路径）；
  现实入口 ≈ npm 供应链投毒
- 被窃 JWT 爆炸半径**不含资金**：7 天窗口内可冒用收藏/存草稿/铸造（铸造免费、NFT 也归
  用户地址而非攻击者）；链上资产无私钥在本系统，动不了钱
- 主网首发用户量小，上线前窗口做三层改造的回归风险 > 收益

**结论**：维持现状（playbook 明示允许"维持现状 + 理由留档"）。
**触发升级条件**：① 引入任何 UGC 富文本 / 第三方脚本注入面 ② P13 Semi 登录正式化改造
登录栈时一并做 ③ 出现有价值的链下资产（如站内余额）。

## C1 — CRON_SECRET 轮换 ✅（2026-07-26 完成并验证）

**背景澄清（反证，省掉一次面板排查）**：生产 `?secret=` 被 `cron-auth.ts:29` 硬拒，而生产 cron
游标持续新鲜 → 各 job **早已在用 Bearer**。P10 遗留待办「cron 切 Bearer」实际早已完成，
C1 因此只是换值，不涉及鉴权方式迁移。

**执行**：新值 43 字符（32 字节 CSPRNG → base64url）。**顺序 = cron-job.org 先、Vercel 后**
——此序下"改一个断一个"，未改的 job 仍正常；反序则 4 个同时全断。

**密钥交付方式（本次刻意设计）**：写入用户桌面文件 + `Set-Clipboard`，**全程不进聊天记录**。
本次轮换的起因正是 2026-05-08 调试时把 CRON_SECRET 打进了聊天——同样的错误不能在修复它的
操作里再犯一次。

**验证三连**：新值 → 200 ✅ / 旧值 → 401 ✅ / 本地 `.env.local` 同步后 → 200 ✅。
**cron 恢复**：`sync-chain-events` 在换后 97 秒内成功更新游标（该 job 每 5 分钟一轮）。
**健康检查**：`/api/health` Bearer 200 —— db ok / lockProvider upstash / mintQueue 0 failed 0 stuck。

**踩坑记录**：第一次验证结果 **100% 反相**（新值 401、旧值 200）= Vercel redeploy 未生效。
env 改动必须 redeploy **且构建跑完**才算数。这个信号很干净——"新旧全反"直接指向服务端 env
未更新，而非密钥值抄错（抄错的话新旧都会 401）。

**附带核实**：用户一并改了 `process-airdrop` 的 header —— 无害。该路由第 26 行有代码级 kill
switch，`AIRDROP_ENABLED !== 'true'` 即刻返回 disabled，早于锁与铸造逻辑；主网口径不变
（删除或 inactive，D 部署日执行）。

**顺带清账**：`.env.local` 重复 CRON_SECRET 定义（STATUS 悬空 TODO）核实为**只有 1 条**，该项作废。

**未做**：`ADMIN_TOKEN` + Alchemy key（调试期泄露）轮换 → 合并为下一次操作。
